# DEXQ — спецификация продукта и реализации

## 1. Назначение

DEXQ — локальный медицинский инструмент контроля качества DXA-исследований. Сервис принимает обезличенные DICOM-файлы, определяет анатомическую область, запускает независимые проверки качества и возвращает понятный структурированный отчёт. Решение не ставит диагноз и не заменяет врача: оно помогает заметить ошибки укладки, позиционирования, охвата и артефакты до клинической интерпретации.

Источник требований: `требования.pdf`. Архитектурный ориентир: `droyti46/mathy-ai`, но без его БД, UoW, репозиториев и контейнера зависимостей — для хакатонного MVP они не нужны.

## 2. Обязательный функциональный контур

- Вход: DICOM, одно исследование содержит до трёх изображений/серий.
- Области: поясничный отдел позвоночника и проксимальный отдел бедра.
- Автоматическое определение области с возможностью явного указания оператором.
- Независимые проверки качества и поддержка нескольких нарушений на одном изображении.
- Выход на изображение: путь/имя, `study_uid`, `image_uid`, область, бинарный класс качества, нарушения, статус и время обработки.
- Ошибки одного файла не прерывают пакет; они попадают в результат как `Failure`.
- Пакетная обработка и выгрузка CSV обязательны для финальной версии.
- Полностью локальный инференс: медицинские изображения не отправляются наружу.
- Целевое время — не более трёх минут на исследование.
- Повторный запуск на одинаковых данных должен давать одинаковый результат.

## 3. Таксономия проверок

| ID | Область | Критерий | Требование | Состояние MVP |
|---|---|---|---|---|
| `spine_coverage` | Позвоночник | Охват | Снизу видны верхние края подвздошных костей, сверху — половина Th12 | Рабочая нижняя ветка из notebook, верхняя ветка будет подключена с итоговым pipeline |
| `spine_tilt` | Позвоночник | Наклон оси | Допустимо до 5° | Рабочая геометрия из notebook; временная детекция оси по интенсивности |
| `artifact` | Обе | Артефакты | Нет посторонних предметов, выраженных наложений | Детерминированный прототип до подключения классификатора ResNet18 + LR |
| `hip_coverage` | Бедро | Позиционирование | Видны большой вертел, шейка и седалищная кость | Контракт и модуль готовы, модель ожидается |
| `hip_rotation` | Бедро | Ротация | Малый вертел имеет корректный размер/контур | Контракт и модуль готовы, модель ожидается |
| `hip_roi` | Бедро | Область интереса | Запас ≥3 см сверху/снизу и ≥2 см по бокам | Контракт и модуль готовы, модель ожидается |

Любая проверка возвращает `passed`, `failed`, `not_evaluated` или `error`. Итоговый `quality_class`: `1`, если найдено хотя бы одно нарушение; `0`, если все применимые проверки завершены без нарушения; `null`, если нарушений нет, но часть обязательных проверок не выполнена.

## 4. Архитектура

### Backend

Стек: Python 3.12, FastAPI, Pydantic, pydicom, NumPy, Pillow.

Простая структура:

```text
backend/app/
  main.py             # создание FastAPI и middleware
  api.py              # HTTP-контракт
  imaging.py          # безопасное чтение DICOM/PNG/JPEG
  schemas.py          # модели API
  analyzer.py         # оркестрация проверок
  checks/
    base.py            # AnalysisContext и интерфейс проверки
    spine.py           # охват и наклон позвоночника
    artifact.py        # артефакты
    hip.py             # проверки бедра
```

Реестр создаётся явно и читаемо:

```python
checks = [
    SpineCoverageCheck(),
    SpineTiltCheck(),
    ArtifactCheck(),
    HipCoverageCheck(),
    HipRotationCheck(),
    HipROICheck(),
]
```

Каждый модуль получает одинаковый `AnalysisContext` и возвращает одинаковый `CheckResult`. Frontend знает только контракт API, а не используемую модель.

### Frontend

Стек: React, TypeScript, Vite, React Router. Без тяжёлой UI-библиотеки. Визуальный язык: глубокий медицинский синий `#0202F1`, белый фон, тонкие серо-синие границы, спокойные статусы, много воздуха. Основной шрифт — Evolventa, заголовки — Evolventa Bold.

Экраны MVP:

1. Лендинг: позиционирование продукта и переход к демо.
2. Анализ: загрузка до трёх файлов, выбор области или автоопределение, предупреждение о локальной обработке.
3. Результат: итоговый статус, предпросмотр, карточки независимых проверок, UIDs и время.
4. О продукте: кратко о клинической логике и ограничениях.

## 5. API v1

### `GET /api/v1/health`

Проверка готовности приложения.

### `GET /api/v1/checks`

Список доступных проверок и их областей. Нужен для документации и диагностики; frontend не строит на нём свою бизнес-логику.

### `POST /api/v1/analyses`

`multipart/form-data`:

- `file`: DICOM, PNG или JPEG; изображения разрешены для локальной демонстрации.
- `anatomical_region`: `auto`, `lumbar_spine`, `proximal_femur`.

Ответ содержит `analysis_id`, безопасные DICOM-идентификаторы, область, `quality_class`, список нарушений, результаты модулей, длительность и локальный preview. Персональные DICOM-теги не возвращаются.

### `POST /api/v1/analyses/batch`

До трёх файлов одним запросом. Ошибка файла сериализуется отдельно, остальные файлы продолжают обрабатываться.

### `POST /api/v1/analyses/batch.csv`

Тот же вход, результат — CSV с колонками из задания.

### `POST /api/v1/analyses/archive.csv`

Принимает ZIP тестового набора, проверяет число файлов и распакованный размер без записи на диск, изолирует ошибки отдельных изображений и возвращает единый CSV.

## 6. Безопасность и приватность

- Данные обрабатываются в памяти и не сохраняются сервером.
- В ответ не попадают ФИО, дата рождения, ID пациента и другие персональные теги.
- Ограничены размер файла и число файлов в пакете.
- Неподдерживаемый/повреждённый DICOM возвращает управляемую ошибку 422.
- В контейнере backend работает не от root.
- CORS в разработке ограничен локальными адресами; production работает через единый reverse proxy.

## 7. Модельный pipeline

`spine_pipeline.ipynb` содержит три независимые проверки поясничного отдела:

- охват: правило нижних боковых областей + последовательность межпозвоночных промежутков;
- ось: SpineNet/ResNet34, крайние центры позвонков и фиксированный порог 5°;
- артефакты: признаки ResNet18 и морфологии + логистическая регрессия;
- итог: логическое OR независимых решений с явным состоянием unknown.

В MVP код отделён от API через модули `Check`. Сначала подключены воспроизводимые части без весов. Следующий шаг — вынести веса, preprocessing и classifier bundle из notebook в `backend/models/`, проверить SHA-256 и заменить временные детекторы внутри соответствующих модулей без изменения API.

## 8. Контейнеризация и запуск

- `backend/Dockerfile` — API.
- `frontend/Dockerfile` — сборка SPA и nginx.
- `docker-compose.yml` — локальный полный стенд.
- `scripts/run.sh` — сборка и запуск для Linux/Unix.
- Версии Python, Node, базовых образов и библиотек зафиксированы.

Минимум для MVP: 4 CPU, 8 ГБ RAM, 5 ГБ диска, без GPU. Рекомендуется для полного pipeline: 8 CPU, 16 ГБ RAM, NVIDIA GPU с 8+ ГБ VRAM и 10 ГБ диска. Финальная целевая конфигурация организатора (H200) заведомо достаточна.

## 9. Качество и ограничения

- Текущие эвристические результаты предназначены для технической демонстрации, не для клинического применения.
- Автоопределение области по DICOM-описаниям может вернуть `unknown`; оператор может задать область явно.
- Для обезличенного набора организатора без `BodyPartExamined` используется воспроизводимый fallback по геометрии кадра (`300 px` для позвоночника, `248–280 px` для бедра); для данных другого аппарата требуется валидация или явный выбор области.
- До подключения обученных весов проверки бедра возвращают `not_evaluated`.
- После подключения моделей метрики считаются раздельно по области и нарушению: sensitivity, specificity, balanced accuracy, F1, ROC/PR AUC и macro-F1; для локализации — Dice/IoU.
- Разбиение train/validation выполняется по исследованию/пациенту, чтобы исключить утечку соседних изображений.

## 10. Критерии готовности ближайшей итерации

- Frontend собирается без ошибок и адаптивен от 360 px.
- Backend читает реальный DICOM, не раскрывает персональные теги и всегда возвращает структурированный ответ.
- Одиночный и пакетный API, а также CSV проверены автотестами.
- Все шесть проверок представлены отдельными модулями.
- SpineNet и artifact classifier подключены из notebook с проверкой контрольных сумм.
- Docker-стенд запускается одной командой и проходит healthcheck.
