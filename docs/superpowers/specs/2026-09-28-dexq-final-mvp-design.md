## Назначение и границы

Локальный технический MVP помогает оператору обнаруживать нарушения качества DXA на DICOM позвоночника и проксимального отдела бедра, видеть объясняющие наложения, вручную корректировать **только** два центра оси позвоночника и выгружать автоматические результаты в CSV. Это контроль качества, не диагностика и не клинически валидированная система. Успех: на исходных DICOM эталонного набора маршрут, сторона, бинарные метки и OR совпадают с неизменённым `QCPipeline.infer()`; для floating-point scores задано численное сравнение с допуском и одним ONNX execution provider. Интерфейс не подменяет ручной правкой результат ML, пакет выдерживает ошибочный файл, медицинские данные и веса не попадают в новые коммиты или внешние сервисы.

## Подход и альтернативы

**Выбрано:** сохранить исходные inference-файлы `combined_qc` из большого архива без изменения алгоритмов; локально держать его ONNX/NPZ runtime и необходимые конфиги с проверкой SHA-256; тонкий адаптер DEXQ переводит вывод в текущий API. Прямой порт моделей внутрь существующих эвристических `checks` повышает риск незаметно изменить preprocessing; замена hip-модуля отдельным ZIP лишает общий пайплайн воспроизводимости. Устойчивую пакетную обработку и интерфейс реализуем снаружи эталона.

## Источники, файловые границы и безопасность

- Из архива в отслеживаемый исходный код переносятся только необходимые для inference Python-модули, конфиги, схемы хешей, короткие агрегированные метрики и документация; вспомогательное обучение и исходные dataset manifests с идентификаторами не публикуются. Перенесённые исходные модули остаются побайтово идентичны эталону. Веса ONNX/NPZ, DICOM, PNG, тренировочные артефакты и построчные метрики остаются **вне Git**.
- Скрипт локальной подготовки извлекает только разрешённые runtime-файлы, сверяет пути, размеры и SHA-256 с эталонным манифестом, не исполняет код из ZIP, не допускает traversal и не публикует вход. Исходный архив обязателен для установки моделей, но не на каждом запросе. При отсутствии/несовпадении весов сервис явно сообщает о неготовности модели вместо тихого fallback к эвристике.
- Проверить совместимость Python 3.12 и фиксированных зависимостей ONNX runtime (`numpy 2.3.5`, `Pillow 12.3.0`, `scipy 1.18.1`, `onnxruntime 1.30.0`, `pydicom 3.0.2`) с доступным окружением; не менять их молча. Для воспроизводимого сравнения выбрать `CPUExecutionProvider` как основной provider и проверять его доступность при старте; GPU-профиль допускается только после отдельной проверки parity. Исходный `QCPipeline` загружается один раз на процесс и синхронизирует обращения собственным lock.
- Локальный `models/` и тестовые изображения не отслеживаются Git. Для финальной сдачи **отдельный** `models/` submission bundle содержит все нужные ONNX/NPZ и манифест SHA-256, включается в комплект судье вместе с кодом (но не в GitHub). `scripts/run.sh` под Linux/Unix проверяет комплект и автоматически подключает его к backend-контейнеру read-only; без весов сборка может пройти, но healthcheck готовности и инференс не считаются рабочими. Зафиксировать базовый Docker image по digest, версии Python/Node, lock-файлов, runtime и provider; проверить запуск офлайн, без внешних закрытых сервисов. `docs/deployment.md` описывает ручную доставку комплекта и минимум/рекомендацию по CPU, RAM, GPU и диску, подтверждённые замером.
- API не сохраняет постоянные исследования. Эталонный runtime принимает пути, поэтому адаптер временно создаёт один входной файл в закрытом локальном временном каталоге, немедленно удаляя его после инференса; никакой сетевой передачи. На API-границе ограничиваются размер, формат, число файлов и архивов, ошибки санитизируются без трассировок и персональных тегов.
- Два архива `data/LCT_data_handoff_2026-09-15*.zip` уже существуют в истории `origin/main` и содержат DICOM. `.gitignore` не удалит их из истории. В текущей задаче новые изображения/веса не коммитить; удаление старых объектов истории и force-push потребуют отдельного решения пользователя.

Группы: норма, `spine_positioning`, `spine_axis`, `spine_artifacts`, `hip_positioning_rotation`, `hip_roi`, сочетания нарушений, без экспертной оценки. Одна запись может находиться в нескольких группах; скрипт исключает метаданные и имена, потенциально содержащие ФИО, из генерируемого индекса, назначает нейтральные имена и фиксирует источник и SHA исходного ZIP. Локальный README объясняет «тестовые для поиграться», наличие пересечений, отсутствие независимого теста и запрет публикации. Генерация идемпотентна, проверяет класс на манифесте и не переносит производные снимки в Git.

## Инференс и API

Для `auto` истинным маршрутизатором служит эталонный classifier. Ручное указание области — отдельный явный путь к соответствующему модулю с предупреждением, что маршрут выбран оператором; hip-side всё равно определяет исходная модель. Данные для моделей передаются из исходного DICOM без текущей процентильной нормализации `imaging.py`. Демонстрационные PNG/JPEG поддерживаются только там, где оригинальный runtime действительно принимает их, иначе возвращается 422. DICOM-теги извлекаются лишь из безопасного списка (Study/SOP UID), не из ответного raw payload эталона.

**Проекция — явная граница поддержки.** ТЗ требует определить и анатомическую область, и проекцию. В 255 DICOM эталонного набора отсутствуют стандартные `ViewPosition` и `PatientPosition`, а эталонный runtime определяет только область и визуальную сторону бедра, **не** проекцию. Значения `projection = "unknown"` и `projection_source = "not_determined"` включить во внутренний и JSON API-контракт; не приравнивать сторону бедра к проекции и не выводить AP/PA из одной только области. Валидированный профиль набора — предоставленные DXA-изображения поясничного отдела и проксимального бедра; подтверждения поддержки иных проекций нет. Для неизвестной проекции на этом профиле не подменять эталонный QC-ответ, но показывать предупреждение о границе применимости. Для подтверждённо иной проекции, если она явно указана в DICOM или выбрана оператором, прекращать QC с `Failure`, а не запускать неподходящую модель. Полное выполнение пункта ТЗ об автоопределении проекции требует отдельной размеченной выборки и классификатора; MVP не выдаёт `unknown` за распознанную проекцию.

Результаты `spine_positioning`, `spine_axis`, `spine_artifacts`, `hip_positioning_rotation`, `hip_roi` отображаются в единый `QualityCheck`-контракт. Старые `hip_coverage`/`hip_rotation` не выдаются за две самостоятельные модели: эталонный hip positioning/rotation — **одна бинарная метка**, без отдельных признаков позиционирования и ротации. По решению пользователя автоматический `violation_type` сохраняет честный код `hip_positioning_rotation`, не дублирует его в два ложных утверждения; выделение `hip_positioning` и `hip_rotation` — открытое ограничение соответствия ТЗ и требует отдельной разметки/модели. Прежний контракт и README обновляются.

`processing_status = Success` разрешён только если все обязательные для выбранной области метки и итог определены; тогда `quality_class` **обязательно `0` или `1`** и совпадает с эталонным OR (`1` при хотя бы одном нарушении, `0` иначе). Если маршрут, обязательная метка или итог неизвестны, вернуть `Failure` и `quality_class = null` в JSON / пустое поле в CSV; `needs_review` без доказанной невозможности оценки остаётся отдельным предупреждением, но не превращается сам по себе в ложный класс. Одиночный endpoint возвращает управляемый 422 для неразбираемого входа, пакет — строку `Failure` с причиной; при uncertainty на декодируемом входе результат может содержать геометрию и причину, но не фиктивный класс. В API остаются название, UID, область, проекция/источник проекции, class, нарушения, статусы, секунды, машинные scores и provenance; пути, потенциальные персональные метаданные и внутренние `raw` не выдаются.

Существующие одиночный и пакетный endpoints и CSV сохраняют обратную совместимость, кроме документированного сокращения фиктивных hip-классов. Одно исследование — группа до трёх изображений по `StudyInstanceUID`; при отсутствующем UID группировка считается неизвестной и не объединяет файлы по имени. UI принимает до трёх файлов **без молчаливого обрезания**; четвёртый и последующие файлы одного UID в пакетном/архивном входе сохраняются в отчёте как отдельные строки `Failure` с причиной «больше трёх изображений»; первые три обрабатываются в стабильном порядке. В браузерном запросе с четырьмя файлами показывается ошибка до отправки, ничего не отбрасывается. Ошибка одного файла становится `Failure`, другие файлы продолжают обрабатываться. Архивный endpoint возвращает одну строку на каждый входной DICOM в стабильном порядке, включая ошибочные, безопасно обрабатывает имена и ZIP-лимиты. CSV строго сохраняет колонки задания: `path_to_study`, `study_uid`, `image_uid`, `anatomical_region`, `quality_class`, `violation_type`, `processing_status`, `time_of_processing`; `path_to_study` — относительный путь файла внутри входного каталога/ZIP (для одиночного файла — его имя), никогда не временный путь. `violation_type` — отсортированные стабильные коды через `;`; `time_of_processing` — секунды для одного изображения от начала чтения/декодирования до готового результата, а не время всего пакета; при parse failure UID допустимо оставить пустыми, но `path_to_study` обязателен. Поле `projection` присутствует в JSON, но не добавляется в обязательные восемь колонок CSV организатора.

## Геометрия, визуализация и ручная коррекция

Ответ для результата содержит исходный PNG для просмотра и минимальный DTO геометрии в `native_pixels_x_right_y_down`: размеры кадра, у позвоночника `axis_line` (верхняя/нижняя точки), `vertebral_candidates` и `gap_lines`; у бедра `foreground_bbox` и пояснение о яркостном proxy. Эталонный `annotated_image` можно показывать как статичный контрольный режим, не смешивая с редактируемым наложением. У бедра нет анатомической ROI-сегментации или точек. UI не знает названий моделей, а знает только типы наложений и названия проверок.

На исходном изображении пользователь может перетащить две существующие точки оси позвоночника. Клиент пересчитывает только угол по оригинальной формуле `measure_tilt` (нативные x вправо/y вниз, `atan2(dx, dy)`, вертикальная ориентация, строгий порог `>5°` с оговоркой о точном равенстве). Проверяются конечность координат, границы изображения и положение верхней точки выше нижней. Исходные `checks`, `quality_class` и scores не изменяются: рядом отображается отдельно маркированный ручной пересчёт угла и производный ручной итог OR, остальные автоматические проверки остаются как были. Есть сброс. Если двух точек нет, правка недоступна и причина видима. Поправки живут в текущей браузерной сессии, не хранятся сервером; текущий интерфейс сохраняет снимки в `sessionStorage` вкладки до её закрытия, поэтому после завершения работы оператор закрывает вкладку. Отдельный экспорт ручных поправок содержит идентификатор анализа, координаты, угол, исходный и ручной итог и явно помечен как пользовательская оценка.

## Метрики и честная интерпретация

Агрегированные значения читаются из эталонного `combined_qc/outputs/deployment_metrics.json`, не пересчитываются при загрузке снимка и не смешиваются с другой версией hip. Протокол: 255 изображений, 249 с экспертной оценкой; итоговый OR F1 `0.8221` на всех размеченных, spine F1 `0.8824` на 99, hip F1 `0.7789` на 150. В таблицах отдельно sensitivity/recall, specificity, F1, macro-F1 для применимых многометочных агрегатов, balanced accuracy, ROC/PR AUC по применимым подзадачам, число позитивных примеров и охват; AUC для булевого OR не определён. Статистика отражает обучение/development и **не является независимой или клинической валидацией**. `per_image` в архиве содержит truth, prediction и study_id для 255 снимков (102 исследования), поэтому воспроизводимый локальный скрипт **обязательно** рассчитывает 95% percentile cluster bootstrap CI по `study_id` для F1, sensitivity, specificity и других определённых метрик; фиксирует seed, число повторов и обработку вырожденных выборок. В Git сохраняются только агрегаты и методика, не построчные записи. Для ROC/PR AUC подзадач применять CI только к повторениям, где присутствуют оба класса/положительные примеры; долю невалидных повторений раскрывать. Dice/IoU без эталонных масок не показывать.

Отдельные deliverables `docs/metrics.md` и демосценарий содержат архитектуру, состав данных и study-level split, preprocessing, таксономию и OR при нескольких нарушениях, сравнение вариантов модели из проверяемых артефактов (без выдуманных чисел), разбор типовых ошибок, ограничения, доверительные интервалы, скорость, конфигурации и реалистичный следующий этап пилотирования. На заявленной целевой конфигурации benchmark замеряет wall-clock **от начала чтения и DICOM-декодирования до готовых JSON/CSV строк** (preprocessing + inference + postprocessing, без загрузки/передачи по сети); acceptance: **не более 180 секунд на исследование из максимум трёх изображений** при прогретых моделях, отдельный cold-start в отчёте. Любое исключение превращается в контролируемый `Failure`/422 без traceback в ответе; повторный запуск на одинаковом файле и одном provider даёт те же маршрут, метки и OR, а scores сравниваются с `atol=1e-5`, `rtol=1e-4`. Долю успешно обработанных файлов публиковать отдельно, не экстраполировать замеры на H200.

## Проверки, поставка и этапность

1. SHA-256 исходного ZIP, инвентарь разрешённых файлов, целостность и cold-load всех runtime-модулей. Записать версии моделей, пороги, preprocessing, зависимости, digest контейнера и ONNX provider.
2. На реальных исходных DICOM сравнить исходный `QCPipeline.infer()` и адаптер: точное совпадение маршрута, стороны, labels и OR; scores в `atol=1e-5`, `rtol=1e-4` на CPUExecutionProvider. Проверить spine, обе стороны бедра, `needs_review`, иной/неизвестный projection и ошибочные изображения. Контрактные тесты API, UID privacy, успешного бинарного класса, Failure с пустым классом, CSV, batch по Study UID, четвёртого файла и archive; отдельные тесты геометрии и отсутствующих точек.
3. `pytest`, `ruff check .`, `npm run build`, запуск Docker с read-only volume и healthcheck. Браузерная проверка загрузки до трёх файлов, видимой ошибки четвёртого, частичных ошибок, мобильного просмотра, перетаскивания точек, сброса и выгрузки. Benchmark на заявленной конфигурации подтверждает `≤180 с/исследование` в указанной границе, долю успехов и воспроизводимость; если критерий не выполнен, статус «финальный MVP готов» не ставится.
4. README, `docs/deployment.md` (минимальная/рекомендуемая конфигурации с CPU/RAM/GPU/disk и инструкция Linux/Unix), `docs/metrics.md` (study-level CI, сравнение и анализ ошибок), руководство пользователя, описание обучения и предобработки, каталог тестовых примеров, известные ограничения и демосценарий сверяются с реальной реализацией. Проверить доставку отдельного bundle с весами для судьи; пушить небольшими понятными коммитами после проверки, не добавляя большие данные.

**Риски и честные ограничения:** реальный hip не выдаёт анатомическую ROI-разметку, не различает позиционирование и ротацию и не доказывает сантиметровые поля; полноценное выполнение этих категорий ТЗ требует нового компонента и независимой разметки. Проекция не определяется эталонным runtime и не должна выдаваться за известную: формальный критерий автоопределения проекции остаётся невыполненным до отдельной разработки. Ручное изменение оси не меняет исходные ML-решения. Общие метрики архива получены на development/training, не на закрытом тесте. Если запуск эталонных зависимостей, Docker или порог 180 секунд окажется недостижим в текущем окружении, это будет задокументировано как блокер, а не скрыто эвристическим fallback.
